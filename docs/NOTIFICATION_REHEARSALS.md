# Local delivery rehearsals — 27 November 2026

Workspace settings > Notification plans > Local delivery rehearsal adds durable simulation records after independent planning approval. An administrator manually selects an existing exact-rule-revision match and confirms a rehearsal. Engineers can read scoped records/history. Nothing sends or queues email, calls Gmail/SMTP, runs in the background or consumes live match events. Queued means queued for manual local simulation only; outcomes apply to the whole planned group and never prove mailbox delivery.

Each record captures the exact plan revision, independent review, match identity and recipient identity/name snapshots. One record per rule/review/match prevents duplicate rehearsals; idempotent retries return the original receipt. A maximum of 100 rehearsal records per rule bounds this local build. Lists use stable created-time/identity pages of 20. The UI offers the newest 20 matching historical matches, with an explicit omission notice. The API accepts any permitted exact-revision match identity.

Manual outcomes are simulate success, retryable failure or permanent failure; cancellation is available while queued/waiting. First retryable failure waits 30 seconds, second waits 60 seconds, third exhausts the record. The server enforces due time; refresh the UI after the scheduled time. Success/permanent failure/exhaustion/cancellation/blocking are terminal. History records enqueue and every action with its actor, time, note and attempts count. Cancellation/blocking do not increment attempts. Rehearsals remain stored across server restarts; no automatic processing is claimed.

Every non-cancellation command rechecks that the captured plan is still latest, its bound rule head is current, its exact independent approval remains latest, and every planned engineer/admin retains canonical site access. A changed source records a blocked terminal simulation instead of an attempt. GET checks never mutate state. Cancellation can safely close a stale open simulation. New independent review can form a new source for another rehearsal. Demonstration/unsupported email addresses are allowed because no destination is contacted. Email addresses, sender configuration and credentials are not captured in these records.

GET/POST /api/notification-plans/rules/{rule_id}/rehearsals lists/enqueues records. POST requires expected_plan_version, expected_rule_version, expected_review_version, match_id, reason (5–1000 characters) and confirmed:true. GET /{run_id} includes exact captured sources, current checks and full history. POST /{run_id}/control requires expected_version, action simulate_success/simulate_retryable_failure/simulate_permanent_failure/cancel, reason and confirmed:true. GET lists support before_id. Canonical site access applies to every path; writes require admin, CSRF and idempotency. Shared rule-head and recipient locks serialize with plan/review/account changes; record version conflicts return 409. Additional destination, sender, force-send and retry-clock fields are forbidden.

Schema 0022 adds notification_rehearsals and notification_rehearsal_events with source references, deduplication and state constraints. The checked SQLite installer backs up data, refuses a running server, creates empty tables and preserves existing plans, approvals, accounts, MFA, rule/condition data and maintenance records. No real plan is approved, queued or processed during installation or read-only portal verification. Production transport, destination authorization, durable workers, partial-recipient delivery, escalation and real operating acceptance remain future work.
