# Notification plan drafts — 27 November 2026

Workspace settings > Notification plans lets engineers and administrators prepare one versioned plan per saved condition rule. Every saved revision binds to the current exact rule revision and preserves its name, one to ten selected account identities/name snapshots, author, time and reason. Changing the saved rule requires a fresh plan revision. The history remains available in pages of 50.

This increment has no sender, queue, activation, retry worker or escalation. It does not use account-invitation Gmail configuration. Saving a recipient does not grant site access or change an email address. No mail is sent or queued, including historical previews. Activation and delivery require later work and explicit destination/routing authorization.

The recipient directory exposes only names, roles and identities of engineers/administrators with current canonical access to the equipment site. Search is name-based, capped at 100 matching accounts with an explicit truncation notice. Email addresses are never returned, stored in plan snapshots or included in audit notes. Save rechecks each selected account under a lock, so disabled/invited/out-of-site accounts are rejected. Histories retain original names even if an account later loses eligibility. Preview rechecks eligibility and reports only a basic configured-address indicator; this does not verify mailbox ownership or deliverability. Demonstration/local/unsupported addresses are identified without exposing them.

Preview uses the saved plan and an existing match from its exact rule revision. It includes the historical trigger snapshot, current human-review state, draft subject, planned recipient checks and a link to captured evidence. It reports whether the plan references an older rule head. Unsaved form edits block preview. The newest 20 matching historical matches are offered with an explicit truncation notice; the API can preview any permitted exact-revision match by identity. Suppressed readings do not create matches and are not represented as notification events. Nothing is attached to the evaluator or existing condition matches.

GET/POST /api/notification-plans/rules/{rule_id} requires engineer/admin and canonical equipment-site access. POST requires name, recipient_ids, expected_version, expected_rule_version and reason. Writes use CSRF, idempotency, the shared rule-head lock and a scoped audit event. Stale plan/rule versions return 409; invalid or ineligible recipients return 422 without disclosing other sites. GET /history supports before_version. POST /preview requires expected_plan_version and match_id, remains read-only and rejects another rule or revision. Extra activation/sender/template/destination fields are forbidden.
